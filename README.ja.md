# FEIN(FE!N): ローカルとクラウドのハイブリッド・エージェント・ハーネス。

**ローカルとクラウドを組み合わせた、世界初のハイブリッド・エージェント・ハーネス。**

[English](./README.md) · 日本語 · [Español](./README.es.md) · [中文](./README.zh.md)

---

多くのエージェント・ハーネスは、ループのあらゆる部分を同じ高価なベンダーから
買っている。次に何をするかの判断も、3,000 行のテストログの圧縮も、危険なコマンドの
検問も、ひとつの仕事として扱われ、ひとつの値段がつき、ひとつのモデルに送られる。

FE!N はループを **スロット** に分解し、それぞれに別のモデルを割り当てられるように
した。フロンティアモデルが考え、手元の 3B モデルが読む。TypeScript 製、
**ランタイム依存ゼロ**、テスト 185 本。

```ts
import { Agent, Router, AnthropicPort, OllamaPort, defaultTools } from "fein";

const cloud = new AnthropicPort({ id: "cloud", model: "claude-sonnet-5",
                                  apiKey: process.env.ANTHROPIC_API_KEY,
                                  costPerMTokIn: 3, costPerMTokOut: 15 });
const local = new OllamaPort({ id: "local", model: "qwen2.5:3b" });

const router = new Router()
  .bind("think",   cloud)                           // 何をするか決める
  .bind("observe", local, { fallbacks: [cloud] })   // 観測結果を圧縮する
  .bind("verify",  cloud);                          // サブエージェントの変更を検問する

await new Agent({ router, tools: defaultTools() }).run("テストが失敗する原因は?");
```

割り当てを変えてもループのコードは変わらない。全クラウド、全ローカル、あるいは
その混合 — どれも同じハーネスで動き、その差額がいくらだったかを台帳が教えてくれる。

## スロット

| スロット | 役割 | なぜ切り離せるのか |
|---|---|---|
| `think` | 次に何をするか決める | 難しい推論。フロンティアのままにする |
| `observe` | 大量の出力を think モデルが見る前に圧縮する | 出力が入力より小さく、節約が累積し、生データが機外に出ない |
| `verify` | サブエージェントの破壊的な呼び出しを検問する | 稀にしか動かないので、高価でも構わない |
| `title` | セッションに名前を付ける | 些細 |
| `execute` | 委任されたサブタスクを最初から最後まで進める | plan-execute 委任の軽量ティア。既定では未割り当て — 未割り当てのスロットは何も公開しない |

名前は ReAct のものだ。Thought → `think` で、Action を出すのもここ —
ネイティブなツール呼び出しは思考と行動をひとつの補完に融合する。`action`
スロットが存在しないのは、ツールを実行するのがモデルではなくコードだからだ。
Observation → `observe`。`verify` と `title` は ReAct にはない制御プレーンの役割である。

どのスロットにもどのモデルでも入る。各スロットはフォールバック連鎖を持つので、
ローカルのランタイムが落ちてもそのスロットがクラウドに降格するだけで、
セッション全体は止まらない。2 回連続で失敗したポートは代替の後ろへ降格され、
数回の呼び出しごとに探査される — 数えるのは壁時計ではなく呼び出し回数なので、
リプレイは正直なままだ — こうして以後のすべての呼び出しは、
失敗が見えている接続試行を免れる。

**割り当ては既定では静的で、適応ルーティングはスロットごとのオプトインである。**
割り当てにはポリシーを持たせられるが、切り替えの根拠はループが報告する事実だけで、
壁時計や運では決して切り替えない — だから同じトランスクリプトからは同じ決定が
再導出され、すべての決定はトレースと台帳に残る。

- `escalate-on-stuck`(`think` 用):ループの番人がモデルの堂々巡りに気づく →
  同じポートのまま、思考の強度だけを上げる。エポック途中のポート交換は決して
  行わない。プロンプトキャッシュはモデルごとにキーが分かれ、あるモデルの署名付き
  推論ブロックを別のモデルへ再生するとプロバイダのエラーになるからだ。
  `restartTo` を指定すると、このはしごに頂上ができる。全段を使い切った時点で
  ポリシーが早期のコンパクションを要求し、**新しいエポックはより強いポートで
  再出発する** — think モデルの交換が無料になる唯一の境界である。要約からの
  再出発はどのみちキャッシュ費用を払うし、レンズはエポックをまたいで推論を
  再生しないからだ。この切り替えはエポック時点で凍結された事実だけを読むので、
  エポック途中で反転しないことが証明でき、引き継ぎの要約は旧モデルが書く
  (自分のコンテキストをキャッシュ料金で読める)。
- `escalate-on-reject`(`observe` 用):品質ゲートに落ちたローカルの digest は、
  クラウドのポートで 1 回だけ再試行される。observe スロットの呼び出しは毎回
  新しく小さなコンテキストを持つので、この切り替えにキャッシュの利害は一切ない。
- `right-size`(補助スロットのみ):ごく小さなリクエストは、スロットの既定が
  大きなモデルであっても小さなモデルへ送る。

`think` そのものを安全に付け替えられる唯一の場所は **サブエージェント境界** である —
新規コンテキストなので壊れるものがない。使い方は 2 通りある。

- **静的**:`subagents.thinkSlot` を設定すると、すべての子がその割り当てで動く。
- **Plan-execute**(`execute` スロットを割り当てると有効になる):spawn ツールに
  `tier` パラメータが加わり、think モデルがステップごとに埋める — `"light"` は
  サブタスク全体を execute の割り当てで、`"heavy"` は think モデル自身の割り当てで
  実行する。`acceptance` パラメータはプランナーに「完了」の意味を明言させ、
  子はそれに照らして報告する。優先順位は、spawn ごとの指定が `thinkSlot` の設定に
  勝ち、設定が継承に勝つ。

これを試した先人たち共通の 2 つの教訓は、文章ではなくコードで強制されている。
堂々巡りを始めた安いモデルが自力で立ち直ることは稀なので、light ティアの子は
**番人が最初に発火した時点で止まり、何に阻まれたかを報告する** —
エスカレーションも、再分割も、そのステップを自分でやるのもプランナーであり、
ハーネスが勝手に経路を変えることはない。また、委任の質はモデルの生の判断ではなく
分解から生まれるので、tier の指針はツールスキーマと、`execute` が割り当てられて
いるときにだけ存在する凍結プロンプト区画に置かれる — そうでなければ、
この機能全体のコストは 0 トークンである。

```jsonc
// config: the object form of a binding carries the policy
"bind": {
  "think":   { "port": "cloud", "policy": { "kind": "escalate-on-stuck" } },
  "observe": { "port": "local", "policy": { "kind": "escalate-on-reject", "to": "cloud" } }
}
```

**もうひとつスロットがあったが、削除した。** `toolformer` は think モデルの一行の意図を
具体的な引数へ変換するものだった。実測すると、**呼び出しごとに think モデルの出力トークンを
11〜15 増やし、節約はゼロ**だった — 意図は引数をそのまま含まなければならないので、
構造上つねに置き換え対象の上位集合になる。数字付きの記録は
[DESIGN.md](./DESIGN.md) にある。教訓は
**委譲先が与えられた以上のものを生み出せるか、呼び出し側が知らない何かを知っている場合にのみ委譲せよ。**

## サブエージェントか、スロットか

対立するものではない。違いは **どれだけ制御を手放すか** にある。

| | 単位 | 固定コスト | 手放すもの |
|---|---|---|---|
| **サブエージェント** | タスク全体 | 起動ごとに約 600〜900 トークン、新規コンテキスト、コールドキャッシュ | 途中のすべての判断 |
| **スロット** | ひとつの判断の中の一段階 | 約 150 トークン | 何も手放さない |

40 ファイルを読んで 1 つのシンボルを探す → **サブエージェント**。
「*この*コマンドを実行せよ、ただし出力は 2 万トークン」→ **スロット**。
これをサブエージェントに渡すと、どのコマンドを選ぶかまで一緒に渡すことになる。
自分で数回ツールを呼べば済む → **どちらでもない**。

## キャッシュを温かく保つ

ハイブリッド実行には、純クラウドのハーネスには存在しない落とし穴がある。
プロバイダがすでにキャッシュした履歴を書き換えることで、
**節約したつもりが余計にかかる**という事態が非常に起きやすい。
FE!N はプレフィックスの安定性を努力目標ではなく不変条件として扱う。

- **レンダリングの単調性** — すべてのレンダリングは前回を厳密に延長する。
  `PrefixGuard` が各レンダリングをハッシュ化し、破れた瞬間に、
  原因となったスロット名とともに報告する。キャッシュミスは請求書ではなく、
  再現可能なバグになる。
- **検査されるプロンプト区画** — システムプロンプトは揮発性を宣言した名前付きの
  区画から組み立てられ、`SectionGuard` が「凍結」宣言された区画の変化を捕まえる。
  `PrefixGuard` は *4 番目のメッセージでプレフィックスが壊れた* と言い、
  `SectionGuard` は *`identity` 区画がターン間で変わった* と言う。後者は手が打てる。
- **ルックバックを考慮したアンカー** — ブレークポイントが遡れるのは
  **コンテンツブロック 20 個** まで。並列ツール呼び出しが 6 つあるターンは
  13 ブロックになる。そんなターンが 2 つ続けば前のアンカーは射程外に出て、
  以後ずっと全額を、しかも黙って払い続けることになる。
- **編集ではなく追記** — `registerDeferred` + `surfaceTool()` はツールブロックに
  触れずにセッション途中でツールを増やし、`injectContext()` は
  システムプロンプトを書き換える代わりに system ロールのメッセージを足す。
- **スライディングウィンドウではなくエポック** — 古いメッセージを落とすと
  それ以降の全トークンがずれ、*以後のすべてのターン*で永久にミスする。
- **順序付き並行実行** — 並列ツールの結果は完了順ではなく **呼び出し順** で追記される。
  トランスクリプトがマシンのタイミングに依存してはならない。

## 観測結果に上限を設ける

2 つの仕組みを意図的に重ねている。無料のほうが先に走るべきだからだ。

**Spill**(モデル不使用):大きすぎるツール出力を `.fein/spill/` に書き出し、
先頭と末尾のプレビュー + モデルが `grep` できるパスに差し替える。
無損失、冪等、上限を超えず、決して増えない。

**Digest**(推論 1 回):ローカルモデルが全文を意味的に圧縮する。

この 2 つは補完関係にあり、テストフィクスチャがそれを証明している —
332 行のログで唯一の失敗が 241 行目にある場合、プレビューは **それを見落とし**、
observe モデルは見つける。だから両方を走らせ、レンズは
`digest → preview → raw` の順に優先する。spill は observe モデルの最悪の性質も直す。
細部を落とした要約に、原典へ戻る道ができるからだ。

Digest は **observe モデルのコンテキストウィンドウに合わせて分割** され、
分割数の上限は locality によって変わる — ローカルの observe モデルは 16 分割まで読む
(限界費用は自前ハードの実時間だけ)が、クラウドの observe モデルは分割仕事を
**まるごと断る**。spill がすでに無料で被害を抑えているからだ。
この定数こそ、ハイブリッド論の縮図といえる。

## ReAct

ローカルモデルは補助だけでなく **運転** もできる。`ReactPort` はテキスト専用の
モデルを包んで、ネイティブなツール呼び出しのインターフェースとして見せる。
だからループは ReAct の存在を知らない — ツールをプロンプトへ移し、
履歴をモデルが話す Thought/Action/Observation 形式へ書き戻し、
モデルが自前の `Observation:` を捏造する前に生成を止め、
壊れた出力をその場で修復する。

最後の点は ReAct の古典的な失敗で、しかも **無言** で起きる。放っておくとモデルは
平然と `Observation: ファイルの中身は…` と書き、どのツールも生み出していない
結果について推論しはじめる。対策は丁寧なお願いではなく、
機械的な停止シーケンスである。

## ステアリング

動いている最中に入力してよい。その行は **次のターン境界** で届く。
ターンの途中では決して入らない — Action と Observation の間に割り込むと、
ツール結果が来るべき場所にユーザーメッセージを渡すことになるからだ。
2 つ目の `run()` の同時実行は拒否される。2 人の書き手が
トランスクリプト上で交錯すると、メッセージ順序がスケジューリング依存になり、
キャッシュが断続的に、しかもデバッグ不能な形で壊れる。

## ループの衛生

ReAct のループはクラッシュして壊れることは稀で、**続いてしまう**ことで壊れる。
同じツールを呼び、同じ答えを得て、またそれについて推論する。
どのターンも単体では妥当に見え、狂っているのは並びだけであり、
モデルは内側から自分のループを見ることができない。

`LoopGuard` は反復、振動(A→B→A→B)、停滞を検出する。判定基準は
**同じ呼び出しで同じ結果** — 答えが変わる呼び出しの繰り返しは正当なので
(ビルドのポーリング、不安定なテストの再試行)、正常な作業では発火しない。
各問題の警告は 1 回だけ。自分を繰り返す番人は、それもまたループである。

ターンを使い切ったときは、残骸を返すのではなく **ツールを一切与えずに**
本物の答えを要求する。能力を取り上げるのは保証であり、お願いは要求にすぎない。

## ループの外側

すべてワークスペースから自動検出される。設定ファイルは要らない。

**永続セッション**(`node:sqlite`、依存ゼロ)。`fein chat --resume <id>` で再生する。
圧縮は **フォーク** である。エポックが要約を種として子セッションを生み、
親は全イベントを保持し、その連結が記録される。「圧縮された」は *失われた* ではなく
*移された* を意味する。ツール呼び出しとその結果の間で中断されたセッションは
再開時に修復される。そうしなければ、単に劣化するのではなく **永久に再開不能** になる。
応答のないツール呼び出しは、どのプロバイダも拒否するからだ。

**想起** — 過去の全セッションを FTS5 で検索する。モデルの背後で勝手に注入するのではなく、
`session_search` として提示する。ツール出力は意図的に索引化していないので、
想起はログ行ではなく決定を返す。

**アイデンティティと規約** — `~/.fein/SOUL.md` はエージェントが何者かを書くもので、
*あなたのもの* だから信頼される。リポジトリ内の `SOUL.md` は他のプロジェクトファイルと
同じように囲われる。信頼境界はファイル名ではなく **誰が書き込めるか** で決まるからだ。

**スキル** — 再利用可能な手順を Markdown で書く。*索引* は凍結プロンプトに常駐し、
*本文* は必要時に読み込む。全本文を先読みすると使わないスキルにトークンを払うことになり、
さらにスキルを 1 つ書くたびにキャッシュ済みの全会話が無効になる。

**フック** — `.fein/hooks/<event>/` に置く関数または実行ファイル。`beforeTool` は
**拒否できる**。観測しかできないフックは安全機構ではなくログ機構である。
観測系フックの例外は無視されるが、`beforeTool` の例外は **拒否側に倒れる**。

**サブエージェント** — 深さの上限は *コードで* 強制し、`SpawnBudget` を木全体で
参照共有する。エージェントごとの上限は上限ではない。breadth^depth で増えるため、
「上限 3」から 40 体が実測された。

**定期ジョブ** — 対話時と **同じ** 権限機構の下で動く永続 POSIX cron。
`--write` を渡さない限り読み取り専用。取りこぼしの遡及実行はしない。
夜通し閉じていたノートを開いても、保留 11 件ではなくゼロ件で目覚める。

```bash
fein chat [--resume <id>]     fein run "<prompt>"     fein demo
fein sessions list | show <id> | search <q> | lineage <id>
fein skills list | show <name>          fein hooks
fein cron list | add | rm | enable | disable | runs | run | serve
```

## テストとベンチマーク

```bash
npm test               # 185 テスト
npm run bench          # オフライン・決定的・無料 — 仕組みのコスト
npm run bench:live     # 実モデル — 正しさの検証
```

ベンチマークは、各仕組みが勝つべき場面と、コストにしかならない場面の両方を
含むタスクで対照群と比較する。実測では observe モデルは
**得意な場面で 88% 安く、役に立たない場面では 43% 高く**、4 タスク合計で **−58%**。
導入直後に、observe モデルが実行され課金されながら出力が黙って捨てられていた
バグを捕まえ、その時点で元を取った。

Node 22.5 以上が必要(組み込みの `node:sqlite` を使うため)。

## 参考にしたプロジェクト

FE!N は 4 つのオープンソース・ハーネスを並べて読んだうえで作られた。すべて
MIT ライセンスである。**コードは一切コピーしていない** — 価値があったのは設計判断であり、
採り入れたものはすべて独自の不変条件とテストを備えた新規実装である。
何を採り、何を退け、何が検証を経て変わらなかったかは
[COMPARISON.md](./COMPARISON.md) に記録した。

- **[deepseek-harness](https://github.com/deepseek-ai/deepseek-harness)** —
  「すべてはプラグイン」。**spill**(モデル不使用の、上限付きプレビュー + 取得用パス)、
  モデル不使用の結果剪定、ループ衛生の番人、そして
  「順序はキャッシュのプレフィックスなので正準でなければならない」という原則を学んだ。
- **[pi](https://github.com/earendil-works/pi)** — 階層化されたエージェント・パッケージ群。
  **ターンを一級の概念として扱うこと**(1 回のアシスタント応答とそのツール呼び出し)と、
  入れ子構造のイベント分類を学んだ。
- **[nanobot](https://github.com/HKUDS/nanobot)** — 意図的に小さく読みやすいコア。
  **ステアリング**(競合する 2 つ目の実行ではなくキュー経由のターン中メッセージ注入)、
  型付きターン、そして永続履歴を安全に再生するための防御的な前処理を学んだ。
  最後の点から、中断されたセッションが永久に再開不能になる実バグが見つかった。
- **[hermes-agent](https://github.com/NousResearch/hermes-agent)** —
  インフラとしてのセッション、深いコンテキスト工学。**名前付きプロンプト区画**
  (これにより我々自身の看板である不変条件が、慣習から検査対象へ変わった)、
  圧縮系譜の根から導く **ローテーション耐性のあるキャッシュスコープ**、
  文字数推定ではなくプロバイダの実使用量を使うこと、
  エラー本文の読み取りに上限を設けることを学んだ。

Claude Code と Codex の公開された挙動、および `src/cache/limits.ts` に
符号化されたブレークポイント・ルックバック・TTL・最小プレフィックスの各規則については
Anthropic のプロンプトキャッシュ文書も参照した。
